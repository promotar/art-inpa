# خطة تنفيذ مشروع Art INPA النهائية

## Production Frontend Build Contract - 2026-07-26

- `public/build` and `public/hot` are generated runtime artifacts and remain
  excluded from Git and Docker build contexts.
- Every production image must generate and verify
  `public/build/manifest.json` during its build phase. Laravel must never start
  and discover a missing Vite manifest at request time.
- Laravel uses its framework default public root, `base_path('public')`. No
  service provider, deployment adapter, plugin, or web server may redirect
  `public_path()` to a sibling directory.
- Vite resolves the manifest relative to that public root as
  `public/build/manifest.json`; browsers request the generated files through
  `/build/...`.
- Coolify/Nixpacks uses repository-root `nixpacks.toml` as the frontend build
  contract: install build dependencies, remove a development hot marker, run
  Vite, and fail the image build if the manifest is empty or absent.
- `package.json` pins the Nixpacks/Node build runtime to Node `22.x`, matching
  Vite 7 requirements and the Docker frontend builder.
- The PHP Docker image contains an immutable Vite build produced by a Node
  builder stage. Source bind mounts may hide image files, so the entrypoint may
  copy this already-verified artifact into an empty mounted `public/build`.
- Production startup must not install Node.js, run npm, access external package
  registries, or hide frontend build failures. A broken image exits with an
  actionable error.
- Core release versioning is environment-driven through `PLATFORM_VERSION`.
  Every completed Core change increments the semantic version before
  deployment: patch for compatible fixes, minor for backward-compatible
  capability, and major for breaking plugin/API contracts.
- Current Core release: `2.5.1`. This public-root and deployment correction is
  backward-compatible with plugins targeting `>=2.5.0 <3.0.0`.

## ملاحظة تشغيلية محدثة - Page Builder / Theme Builder

- محرر Page Builder وTheme Builder يجب أن يعرض نفس HTML/CSS الذي يظهر في مخرج الموقع الحقيقي، خصوصاً للهيدر والفوتر والقوالب العامة.
- إذا كان `page_builder_json` مخزناً كـ export wrapper وليس GrapesJS project مباشر، يجب على النظام تجاهله كـ project والرجوع إلى HTML/CSS المحفوظ حتى لا يظهر الكانفس فارغاً.
- كل web server يجب أن يخدم مجلد `public` الموجود داخل جذر مشروع Laravel. أي asset منشور مثل `vendor/front-builder/page-builder/page-builder.js` يبقى نسبة إلى مجلد `public` نفسه ولا تتم مزامنته إلى مجلد شقيق خارجي.
- لا يجوز أن يكسر نقص إعدادات widget schema تحميل المحرر؛ يجب أن تتعامل واجهة الإعدادات مع العناصر الناقصة بشكل fail-open داخل المحرر.
- المرحلة الحالية من تحويل Page Builder إلى Schema-first تعرض فقط العناصر الجديدة: Container وHeading وImage. العناصر القديمة تبقى في الكود للتوافق والتدرج، لكنها ليست مصدر الحقيقة للعناصر الجديدة الظاهرة في المحرر.
- أي Widget جديد لاحقاً يجب أن يملك تعريفاً موحداً كاملاً: `type`, `label`, `icon`, `category`, `default_props`, `general_schema`, `style_schema`, `advanced_schema`, `supports`, `editor_preview_renderer`, `frontend_renderer_reference`.
- لا يجوز تسجيل Widget جديد في المحرر إذا كان ناقص General أو Style أو Advanced schema.
- تصميم العناصر الجديدة يجب أن ينتج من props/schema/style engine، وليس من HTML/CSS ثابت أو classes مفروضة داخل الكور.
- Phase 1C من Page Builder Schema-first أعادت تنظيم واجهة التحرير إلى وضعين واضحين: Browse لعرض Elements/Layers فقط، وEdit لإعدادات العنصر المحدد فقط. عناصر المرحلة الحالية ما زالت Container وHeading وImage فقط، وأي تعديل في الخصائص يجب أن ينعكس مباشرة في الكانفس ثم يحفظ داخل `project_json` كمصدر الحقيقة.
- Phase 1D من Page Builder Schema-first أصلحت ربط Style Binding لعناصر Container وHeading وImage، وحسنت Controls الخاصة بالأبعاد والألوان. يجب أن تبقى القيم من مصدر واحد: control value -> prop -> `data-pb-*` -> generated CSS -> preview/publish output.
- Phase 1E من Page Builder Schema-first أصلحت مسار الأداء: لا يجوز أن تعيد style-only controls بناء preview markup أو تضاعف dirty/update events. إعادة توليد CSS الكامل تبقى عند save/autosave/publish فقط، والتعديل المباشر في الكانفس يجب أن يبقى خفيفاً ومحصوراً بالعنصر المحدد.
- Phase 1E Image Widget اكتملت ضمن نفس المرحلة بدون إضافة Widgets جديدة: Image يستخدم `pb_image` كـ component type مستقل، ويقرأ الصور من Media Library الرسمي عبر `admin.media.index`. أي اختيار صورة يجب أن يحفظ `media_id`, `media_url`, `thumbnail_url`, الأبعاد، mime/type، alt، caption، link، loading/decoding داخل props/schema، ولا يجوز اعتبار أبناء الصورة مثل `a`, `img`, `figcaption` Widgets مستقلة أو حقن schema props فارغة عليهم.
- LMS frontend courses catalog is plugin-owned. The public `/courses` route, `/lms/courses/catalog` JSON endpoint, frontend assets, frontend menu entry, and Page Builder widget `lms.courses-catalog` live in `modules/lms`. The Page Builder page `platform_pages.slug=courses` uses this plugin widget placeholder, and LMS frontend JS hydrates it from the LMS API. Core Page Builder files must not be edited for this LMS catalog unless a future architecture change explicitly approves a shared dynamic-renderer extension point.
- ترحيل كورسات المنصة التعليمية القديمة يتم من موقع WordPress/MasterStudy `learn.art-inpa.com` إلى جداول LMS الجديدة. المصدر العملي المستقر هو REST API العام `https://learn.art-inpa.com/wp-json/ms_lms/v2/courses` و`/course?id={id}`. بيانات cPanel موجودة في ملف الأسرار المحلي، لكن عند آخر تحقق لم تقبل تسجيل الدخول؛ لذلك يجب عدم افتراض توفر قراءة ملفات/قاعدة ووردبرس إلا بعد تحقق وصول جديد. الاستيراد يحفظ الصور محلياً في `storage/app/public/lms/course-images/import-masterstudy` ويربط الدروس بسلاسل `masterstudy-course-{course_id}-lesson-{lesson_id}` لمنع دمج الدروس المشتركة بين الكورسات.

# 24. تحديث AI Assistant Agent - 2026-06-28

تم تطوير مساعد الذكاء من شات بسيط إلى Agent داخل المنصة:

- يدعم رسائل متعددة الأسطر.
- يدعم رفع الصور والملفات من الفرونت والداشبورد.
- يوجه النية إلى أقرب أداة: دردشة، توليد صورة، تحليل صورة، بحث موقع/داتابيس، مساعد كود، أو تقارير إدارية.
- يعرف المستخدم الحالي ورولاته وصلاحياته من Laravel فقط.
- لا يثق بادعاءات المستخدم؛ بيانات الموقع وقاعدة البيانات هي مصدر الحقيقة بعد فحص صلاحيات Laravel.
- يمنع وصول AI Gateway المباشر إلى قاعدة البيانات.
- كل بحث في بيانات المنصة يتم عبر أدوات Laravel مسجلة ومحددة ومراجعة بالصلاحيات.
- البحث العام في محتوى الموقع والمقالات مسموح للبيانات المنشورة فقط.
- المستخدمون والرولات والتقارير الإدارية لا تظهر إلا لمن لديه صلاحية.
- تحليل الصور يعمل الآن تقنياً عبر Vision Worker، أما التحليل الدلالي الكامل وOCR فيحتاجان تفعيل موديل Vision/OCR على AI Server لاحقاً.

# 25. Blog Plugin operational behavior - 2026-06-28

Blog posts are managed from the admin Blog editor, but the canonical published article route is public:

- Public article: `/blog/{slug}`
- Category archive: `/blog/category/{slug}`
- Tag archive: `/blog/tag/{slug}`

Admin preview is only for drafts, scheduled posts, private posts, or non-public content. When a post is already published, public, and not scheduled for the future, preview actions redirect to `/blog/{slug}` so the final article URL is crawlable and shareable.

The Blog editor must not expose decorative controls. Any visible button, tab, or field must either save real data or perform a real action. Validation failures must show a clear summary, highlight invalid fields, and scroll/focus the first invalid field so admins can correct the issue without guessing.

Blog editor media must use the platform Media Library (`admin.media.*`) as the source of truth. New featured images are saved by public media URL so the frontend can render them without depending on Blog-specific media rows. Revisions are limited to the latest 4 per post and can be deleted individually by admins.

# 26. Art INPA AI Assistant Governance - 2026-06-28

Art INPA AI Assistant is a governed Laravel assistant inside the platform, not a generic model identity.

Core rules:

- Public identity is always `Art INPA AI Assistant`.
- Laravel routes intent before any general chat response.
- Practical requests use registered tools when available.
- Tool results become conversation memory objects.
- Generated and uploaded images are remembered as visual context.
- Follow-up visual messages such as `حللها`, `وين الفنان`, or `اعملها مرة ثانية` reuse the last visual tool result instead of going to general chat.
- Platform data access always passes through Laravel permissions and whitelisted tools.
- The assistant must not invent unavailable abilities. If NFT, image editing, or upscaling tools are not connected, it says that clearly.
- The model never directly updates database records or directly queries platform data.

Implementation:

- `AiConversationService` stores `tool_results`, `last_tool_result`, `last_visual_result`, and `last_visual_prompt` in `ai_conversations.metadata`.
- `AiIntentRouter` resolves visual context follow-ups before fallback classification.
